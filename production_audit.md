# Production Readiness Audit — ACP Commerce Platform

Use this prompt with Claude Code (or work through it manually) against the actual repo.
Run it in order — sections build on each other and are ranked by risk, not alphabetically.

---

## HOW TO USE THIS

Paste this whole document into your agent (Antigravity, or any coding agent
with repo access) with this instruction attached:

> "Audit this codebase against every section below. For each item: show me the
> actual file/line evidence (not a guess), mark it PASS / FAIL / UNVERIFIED,
> and if FAIL, show the minimal fix. Do not mark anything PASS without quoting
> the code that proves it. If you can't find relevant code, say UNVERIFIED —
> don't assume it exists. Do not summarize optimistically — I specifically
> want disagreements, gaps, and unproven claims surfaced, not a clean report."

That last instruction matters more than it sounds. Agentic coding tools have
a strong bias toward returning a confident, complete-looking summary — you saw
this already with the "YES! 100%" response earlier in this conversation. The
explicit instruction to prefer UNVERIFIED over an assumed PASS is what
counteracts that.

If Antigravity works across multiple files/agents in one session, run this in
a fresh session rather than continuing from whatever session built the
bulk-upload endpoint — you want a reviewer with no incentive to validate its
own prior work.

## SECTION 1 — Data Isolation & Multi-Tenancy (highest risk first)

1. For every read path (listings, orders, customers, search) in every service,
   confirm `merchant_id` (or `tenant_id`) is enforced **inside the query itself**,
   not applied after fetching or left to the caller.
2. Confirm the vector store (ChromaDB) queries use a `merchant_id` metadata
   filter on every search call — not just the SQL side of hybrid search.
3. Confirm the AI agent/orchestrator threads merchant context through every
   tool call (`search_listings`, `get_listing_details`, `check_availability`,
   etc.) as an explicit parameter, not just as frontend widget config.
4. Confirm there's no endpoint where a merchant's JWT/session could be used to
   query another merchant's `merchant_id` by passing it as a parameter (IDOR check).
5. Live test: create two merchants, one distinct product each, search as
   merchant A for a term only merchant B's product matches. Must return nothing.

## SECTION 2 — Error Handling & Failure Modes

1. Find every `except Exception: pass` (or bare `except:`) in the codebase.
   Each one is a candidate silent failure — list all of them with file/line.
2. For the bulk-upload endpoint specifically: does one malformed row
   (missing field, wrong type, bad encoding) crash the entire batch, or does
   it skip gracefully and report which rows failed?
3. For every external call (Celery, Chroma, payment gateway, webhook delivery):
   what happens on timeout or connection failure? Does the user get an honest
   error, or a false "success"?
4. Are there retries with backoff on transient failures (DB connection drop,
   Chroma unavailable), or does a blip cause permanent data loss?
5. Does the checkout/payment flow have idempotency keys to prevent double-charge
   on retry or network failure?

## SECTION 3 — New/Unverified Code (anything added without a human running it)

1. List every endpoint or module that was generated by an AI session but has
   no corresponding test and no evidence of manual execution.
2. For `bulk-upload` specifically: has it been run against a real messy file
   (bad encoding, missing columns, wrong types, duplicate SKUs)? If not, mark
   UNVERIFIED regardless of how complete the code looks.
3. Cross-check: does new code follow the same patterns (auth, merchant scoping,
   error handling) as the established endpoints, or does it diverge?

## SECTION 4 — API Contracts & Backward Compatibility

1. List all existing API routes. Confirm none were modified in a way that
   breaks existing request/response shapes (per your own "keep existing APIs
   working" rule).
2. Are API versions pinned (`/api/v1/...`) with a clear path to `/v2` for
   breaking changes, or is everything mutating `v1` in place?
3. Is there an OpenAPI/Swagger spec that's actually in sync with the code,
   or stale?

## SECTION 5 — Database & Migrations

1. Is every schema change backed by a migration file (Alembic or equivalent)?
   Can the DB be rebuilt from migrations alone, or does it depend on manual
   steps / seed scripts that aren't idempotent?
2. Are there foreign key constraints enforcing `merchant_id` relationships,
   or is isolation purely application-logic (no DB-level backstop)?
3. Are there indexes on `merchant_id`, `sku`, and whatever fields power search
   filters? (Check `EXPLAIN ANALYZE` on a listing search query.)
4. What happens on a failed migration mid-deploy — is there a rollback path?

## SECTION 6 — Security

1. Auth: is every write endpoint behind `require_permission` or equivalent?
   List any endpoint that isn't.
2. Are API keys / OAuth tokens stored encrypted at rest, not plaintext in DB?
3. Is there rate limiting on public-facing endpoints (chat, search) to prevent
   abuse or cost blowout on LLM calls?
4. Input validation: does the bulk-upload endpoint sanitize/validate file size
   and content before parsing (protection against a 500MB CSV or malicious payload)?
5. Are secrets (API keys, DB creds) in environment variables / a secrets
   manager, or hardcoded/committed anywhere in the repo?

## SECTION 7 — Observability

1. Is there structured logging (not just `print`) with request IDs that let
   you trace one conversation/request across services (agent_server →
   merchant_server → payment_server)?
2. Are there health check endpoints (`/health`, `/ready`) on each service?
3. Is there any metrics/monitoring (even basic) on: LLM call latency and cost,
   search index sync success/failure rate, checkout failure rate?
4. If a merchant's catalog fails to index into Chroma silently, would you
   currently find out — or only when a customer complains nothing's searchable?

## SECTION 8 — Testing

1. What's actual test coverage on: checkout flow, bulk-upload, merchant
   data isolation, orchestrator tool-calling? (Not aspirational — what exists.)
2. Are there integration tests that run the full conversation loop
   (search → clarify → compare → cart → checkout) end to end, or only
   unit tests on isolated functions?
3. Is there a CI pipeline that runs these tests on every push, or is testing
   manual/ad hoc?

## SECTION 9 — Scalability & Infra Readiness

1. Are agent_server, merchant_server, payment_server independently deployable
   and horizontally scalable, or do they share in-process state that would
   break under multiple instances?
2. Is ChromaDB running as a shared service, or embedded per-process (which
   would break under horizontal scaling)?
3. Is there a queue (Celery/RabbitMQ) actually decoupling slow operations
   (indexing, notifications) from the request path, and is it monitored for
   backlog/dead letters?
4. What's the actual cold-start and per-request cost of LLM calls in the
   orchestrator — is this sustainable at 10x current merchant count?

## SECTION 10 — Documentation & Operational Readiness

1. Is there a runbook for "search isn't returning results for merchant X" —
   i.e., can you debug a production incident without re-reading the whole
   codebase under pressure?
2. Is there a clear merchant onboarding doc (what fields are required, what
   formats are supported) that matches what the code actually accepts?
3. Are environment setup / deployment steps documented well enough that
   someone else (or you, in six months) could redeploy from scratch?
